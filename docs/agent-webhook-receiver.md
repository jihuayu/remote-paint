# Agent Webhook receiver inbox

`createAgentWebhookInbox` is a private backend receiver primitive. It owns a separate SQLite file in an owned `0700` directory, with an exact `0600` regular file, one hard link, pinned device/inode, exclusive ownership, DELETE journals and FULL synchronization. It does not open a Source database or invoke business handlers. The caller configures one tenant and endpoint, at most two copied signing keys, and an active key ID. Authentication uses the original bounded bytes and the existing signature age/endpoint/event-ID binding.

`accept({eventId,signature,body})` authenticates first, decodes strict UTF-8, and validates an exact `agent-webhook-v1` envelope. It accepts the sender's compact JSON.stringify representation only; whitespace, duplicate members, BOMs, malformed metadata and private fields fail. The shared `parseAgentEventBody` validator enforces metadata and state consistency without requiring Source records. The Source journal retains its additional parent run/tenant/session, invocation ownership, immutable tool, state history and original creation-time checks.

Acceptance commits the original body/hash before returning `{status:202,duplicate:false,ack}`. The ACK has exactly `{schema:"agent-webhook-ack-v1",eventId,bodySha256}`. Identical event IDs and bytes return status 200 and the same ACK after restart. Different bytes for an existing ID, another ID for the same run sequence, or changed fixed subscription/session/region/version fail with `CONFLICT`. Inbox storage proves acceptance only: it does not verify underlying closure evidence, prove application execution, reconcile missing Source history or release a Source reservation.

Retention defaults to 1024 events and a 16 MiB database, with hard configuration limits of 10000 events and 64 MiB. Both limits, tenant, endpoint and instance ID are persisted and must match on reopening. At event capacity, new IDs fail with `CAPACITY`; duplicates remain acknowledgeable. No automatic deletion, eviction or counter reset occurs. SQLite's page limit bounds the database; its rollback journal is additional bounded disk use. An uncertain storage result fences further work with `WRITE_UNKNOWN`/`FAULTED` and requires closing and reopening the exact original file for validation. Invalid, empty pre-existing or corrupt files are retained and rejected, never replaced with empty state.

`read({after,limit})` returns detached metadata in local acceptance order, at most four events per page. This cursor is a local inbox position, not Source sequence continuity or business completion. `identity()` exposes the fixed storage binding; `close()` releases the database and zeros the authenticator's owned key copies. The private directory is trusted against same-user tampering; identity checks detect replacement but are not a filesystem sandbox.

An existing SQLite ledger is never opened or closed through an extra raw descriptor: POSIX close could release another connection's process-owned advisory locks. A regression test verifies that a failed second in-process opener cannot admit a third process while the first owner remains live.

## Owned HTTPS receiver

`createAgentWebhookReceiver` owns a TLS HTTP/1.1 listener and its private inbox. Configure the inbox fields plus `cert`/`key` PEM (each at most 32768 bytes). The bind `host` must be a literal IP (default `127.0.0.1`), `port` defaults to 0, and the exact `path` defaults to `/webhooks/<endpointId>`. `listen({signal})` reports the actual bound address; `close({signal})` fences admission and waits for original resources and database closure. Signals cancel only observation, including an already aborted signal. The caller must close the returned owner after a bind failure; listen failure never discards its inbox. The listener uses an exclusive bind and TLS 1.2 or newer; it does not share a cluster listener.

The default connection limit is 8 (hard 32), including TCP clients that never start TLS. Each admitted connection has an absolute lifetime from its original TCP connection event, default 30000 ms (50..60000 ms). Slow handshake, header/body bytes and ACK writes cannot renew it. The receiver reserves original TCP records until their actual close, and established TLS streams, requests and responses have separate close receipts. Admission is fenced at the Node listener while an old transport is still retiring. Node 22.13+ supports the drop-all zero-connection setting used here; see [Node maxConnections](https://nodejs.org/docs/latest-v22.x/api/net.html#servermaxconnections).

Before TLS is established, Node's TLS server owns its wrapper. `tlsClientError` can arrive from Node's own close callback, too late to attach a new close listener. The receiver does not create another retained wrapper or wait from that error notification; it keeps the original TCP reservation through its actual close. Closing the receiver additionally waits for Node's listener-close callback. A real test observes `onSocketClose` in that notification's stack, original TCP close events and reacquisition of the same inbox identity; no destroyed/finish flag is accepted as a transport close receipt.

Requests require POST, the exact path, HTTP/1.1, a single canonical Content-Length (1..4096), JSON content type, event ID and signature headers. Request headers are capped at 8192 bytes and 16 fields; a seventeenth field is a rejection sentinel. Duplicate headers, chunked/content-encoded bodies, trailers, Expect, upgrade, CONNECT and pipelined second requests do not enter the inbox. Each accepted connection carries at most one request and the response closes it. The body uses one declared-size bounded buffer. A complete request still must pass inbox authentication, strict canonical envelope validation and durable commit; the adapter returns only the exact inbox ACK for status 200/202. Invalid/auth/conflict/capacity states receive small fixed errors with status 400/401/409/503; errors never reflect raw URL, body, signatures or key material.

The new adapter has 27 real TLS/HTTP lifecycle cases, including the actual dispatcher/Source capture path, close observation cancellation while the database remains locked, malformed/pre-handshake stalls, absolute drip deadlines, header/framing bounds and production receiver SIGKILL before/after COMMIT. An early test observed client TCP connect before server admission and was changed to wait for that actual admission. Drafts that waited for a late TLS close notification stranded resources and timed out; their source and logs are preserved. An attempted TLS prototype event trace did not observe an instance's emissions and was replaced by direct original TCP receipts and Node close-callback stack observations. Existing tests, resource/deadline limits and platform skips are retained.

This checkpoint implements the production adapter; controlled localhost TLS fixtures qualify its behavior. It does not deploy an external endpoint, run a business handler, expose public management/SDK contracts or qualify the original Native runtime.
